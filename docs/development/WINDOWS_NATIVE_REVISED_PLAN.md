## 3. 分层与 owner

共享编辑/文档/坐标/绘制语义 → 主要后端选择 → D3D12 或 D3D11 → Windows 呈现。
主要后端 owner 负责设备代际、提交、资源生命期、失败状态；窗口不各自随意创建另一套后端。
辅助 D3D11 捕获/互操作按需求持有有界租约；无需求时不因双后端能力而创建资源。
捕获与呈现分别报告能力；同设备、同适配器和跨适配器路径分别验证，不默认 GPU→CPU→GPU。

Loom 管包/授权/服务 → 受控包获取与本地缓存 → Otter QuickJS 实例 → 原生 SDK。
本地事件、参数与预览在 Otter 闭环；真正远程服务使用异步请求、取消、超时、进度与晚到隔离。
预览不冒充正式结果。状态保存与正式结果提交 owner 在新合同中逐项确定，不随 JS 移位默认全转 Otter。
既有 Save/Checkpoint 继续是工作区提交 owner，直到有明确且验证过的替代设计。

## 5. 验证与操作边界

每次源码迭代冻结输入，编译/测试/产物绑定同一 SHA；不继承旧源成绩。
内部版本只分配一次；只有全部 Cargo 构建完成后封存产品，集成前后核 target 同字节。
具体性能收益、设备覆盖率、总资源预算必须测量，不承诺 D3D12 必然更快或插件零成本。
当前没有新增依赖、系统安装、ANGLE 默认启用、发布或部署授权。
跨仓库分别核 dirty、diff、格式/行数/合同与运行门；只改文档不伪造程序验证。
允许必要源码修改不等于自动 commit/push、修改真实 profile、删除内容或改变其他客户端的既有协议。

后续必须明确但无需重新推翻主线的设计项：最低能力 profile、Shader ABI、恢复次数/时限、隔离布局、
包信任/共享依赖/离线撤权细节、结果 owner、隐藏驻留与已提交远程服务任务的退出语义。
有新的产品冲突或超出授权的操作再询问用户；一般工程细节由实现方按证据负责。
